# 영상 하나에서 3차원 장면 만들기

```
영상 → 사진 여러 장 → 점 → 알갱이 → 줄인 파일 → 웹 주소
                        └────→ 메시 (물리를 붙이려면)
```

돌아가는 예시가 https://suncreation.github.io/room-3d-demo/ 에 있고,
같은 저장소의 `room3d.ipynb` 가 아래 걸음을 담고 있다.

## 0. 어디서 계산할지 정한다

**두 걸음의 성격이 다르다. 나눠서 정하는 편이 낫다.**

| 걸음 | 필요한 것 | 어디가 나은가 |
|---|---|---|
| 복원 (영상 → 점) | CUDA GPU, 8GB 이상 | GPU 가 없으면 코랩 |
| 알갱이·줄이기 | 별것 없음 | 어디서나 |
| 메시·다듬기 | CPU 코어와 메모리 | **대개 이쪽 기계가 빠르다** |

메시 쪽은 코랩의 vCPU 두 개보다 요즘 노트북이 훨씬 낫다.
같은 일이 코랩에서 수십 분 걸리다 이쪽에서 십몇 초에 끝나는 일이 흔하다.

### 기계부터 살펴본다

```bash
# GPU
nvidia-smi --query-gpu=name,memory.total --format=csv 2>/dev/null || echo "NVIDIA GPU 없음"
# 애플 실리콘인지
sysctl -n machdep.cpu.brand_string 2>/dev/null
# 코어와 메모리
python3 -c "import os,shutil;print('코어',os.cpu_count());print('빈 디스크 GB',round(shutil.disk_usage('.').free/1e9))"
python3 -c "import psutil;print('메모리 GB',round(psutil.virtual_memory().total/1e9))" 2>/dev/null
```

판단 기준이다.

- **NVIDIA GPU 가 있고 여유 메모리가 8GB 이상**이면 복원까지 이 기계에서 된다
- **애플 실리콘**이면 복원은 코랩으로 보낸다. 토치가 돌긴 해도 이 모델 경로가 CUDA 를 전제한다
- **GPU 가 없으면** 복원은 코랩
- 어느 쪽이든 **메시 걸음은 이 기계에서** 하는 편이 빠르다

**어떤 운영체제인지도 함께 본다.** 코랩으로 보낼 때 붙잡는 도구가 여기서 갈린다.
위 명령이 둘 다 빈손으로 돌아오면 Windows 일 수 있으니 확인한다.
WSL 안에서는 `sysctl` 이 없고 리눅스로 잡힌다.

**[물어본다]** 살펴본 결과를 알리고 어디서 돌릴지 정한다.
코랩을 쓰면 구글 계정으로 인증이 필요하고 무료 등급은 GPU 배정이 보장되지 않는다는 점,
이 기계에서 돌리면 시간이 얼마나 걸릴지 가늠한 값을 함께 준다.

### 코랩을 쓰기로 했다면

붙잡는 방법이 둘이다. **사용자 기계부터 가른다. 여기서 잘못 고르면 첫 명령에서 막힌다.**

| 사용자 기계 | 쓰는 것 | GPU 를 누가 고르나 |
|---|---|---|
| macOS, 리눅스, WSL | Colab CLI | `colab new --gpu T4` |
| **Windows** | **Colab MCP** | **사용자가 브라우저에서 직접** |

Colab CLI 문서가 지원 범위를 못 박아 두었다. "the Colab CLI currently supports
Linux and macOS only. Windows is not supported at this time."
**Windows 에서는 CLI 설치를 시도하지 않는다.** MCP 로 간다.
사용자가 WSL 을 쓰겠다고 하면 그때는 CLI 쪽이다.

#### CLI 쪽 (macOS, 리눅스, WSL)

CLI 를 깐다. 파이썬 3.12 이상이 필요하다.

```bash
uv tool install google-colab-cli     # uv 가 없으면  pip install google-colab-cli
colab --help
```

세션을 만든다. 처음이면 브라우저가 열리며 구글 계정 인증을 묻는다.
OAuth 설정 파일을 따로 만들 필요는 없다.

```bash
colab new -s room --gpu T4
colab status -s room
```

쓰는 명령이다.

```bash
colab upload -s room <로컬파일> <원격경로>
colab exec -s room -f <스크립트.py> --timeout 3000
colab download -s room <원격경로> <로컬경로>
colab ls -s room /content
colab stop -s room
```

**`--timeout` 을 넉넉히 준다.** `colab exec` 이 답을 기다리는 기본값이 **30초**라
그보다 긴 계산은 `TimeoutError: Timeout waiting for reply` 로 잘린다.
모델 내려받기만 3분이니 그냥 두면 반드시 걸린다.
한 번에 돌리고 반납하는 `colab run` 은 이 값에 안 걸린다.

**`--gpu` 값을 틀리게 쓰지 않는다.** 받는 값은 `T4`, `L4`, `G4`, `H100`, `A100` 이다.
모르는 값을 주면 조용히 A100 으로 떨어졌다가 그다음 걸음에서 실패한다.

**여러 걸음을 셸 하나로 묶어 돌리지 않는다.** 묶으면 어디서 멈췄는지 안 보인다.
한 걸음씩 돌리고 사이사이 `colab status` 로 확인한다. `BUSY` 가 아닌데 결과가 없으면
전달 자체가 안 된 것이니 다시 건다.

**일이 끝나면 `colab stop` 으로 세션을 끈다.** 안 끄면 계속 자원을 쓴다.

#### MCP 쪽 (Windows)

Colab MCP 는 **사용자가 브라우저에 열어 둔 코랩 노트를 옆에서 모는** 방식이다.
세션을 직접 빌리는 것이 아니라 이미 떠 있는 노트에 셀을 만들어 돌린다.

서버는 사용자의 에이전트 설정에 등록해야 하고, 등록은 에이전트를 다시 띄워야
반영된다. **이건 사용자가 할 일이다.** 파이썬과 깃과 `uv` 가 있어야 한다.

```json
{
  "mcpServers": {
    "colab-mcp": {
      "command": "uvx",
      "args": ["git+https://github.com/googlecolab/colab-mcp"],
      "timeout": 30000
    }
  }
}
```

**[물어본다]** 등록을 마쳤는지, 그리고 아래 둘을 했는지 확인한다.

1. 브라우저에서 코랩 노트를 하나 열었는가
2. 런타임 유형을 **T4 GPU** 로 바꿨는가

**이 둘은 대신 해 줄 수 없다.** 런타임을 고르는 것은 브라우저에서 눌러야 하는
일이라, 확인 없이 진행하면 CPU 런타임에서 복원을 돌리다 한참 뒤에 막힌다.
확인이 끝나면 `open_colab_browser_connection` 을 부른다.

**연결에 성공해야 노트를 다루는 나머지 도구가 열린다.** 도구가 연결용 하나만
보이면 아직 연결 전이거나 브라우저 쪽 노트가 안 떠 있는 것이다.
도구가 안 늘면 노트 탭이 열려 있는지부터 본다.

**파일은 셀 안에서 주고받는다.** CLI 의 `upload` / `download` 에 해당하는 명령이
따로 없으니, 영상은 사용자가 코랩 파일 창에 끌어다 놓게 하거나 셀에서
`google.colab.files.upload()` 를 쓰고, 결과는 `google.colab.files.download()` 로
내려받게 한다.

**세션이 브라우저 노트 그대로다.** CLI 처럼 붙들어 주는 데몬이 없으니, 오래 걸리는
걸음을 걸어 두었으면 사용자에게 그 탭을 가끔 눌러 두라고 알린다.
일이 끝나면 런타임을 끊으라고 알린다.

## 1. 영상을 살펴본다

```bash
ffprobe -v error -select_streams v:0 \
  -show_entries stream=width,height,duration,nb_frames \
  -of default=noprint_wrappers=1 <영상>
```

조건이다.

| 조건 | 왜 |
|---|---|
| **걸어 다니며** 찍었는가 | 제자리에서 몸만 돌리면 시차가 안 생겨 거리를 못 잡는다. 가장 흔한 실패다 |
| **가로**인가 | 세로는 화면 위아래를 천장과 바닥이 차지한다. 둘 다 밋밋해 얻을 것이 적다 |
| **15초에서 20초**인가 | 그 이상은 같은 장면이 되풀이될 뿐이다 |
| 흐리지 않은가 | 빨리 지나가면 흐려진 장이 섞인다 |

세로이거나 너무 짧거나 길면 **[물어본다]**. 그대로 진행할지, 다시 찍을지 정한다.
자세히 보고 싶은 곳이 있는지도 함께 묻는다. 있으면 그 앞에서 좌우로 한두 걸음
더 움직여 찍는 편이 낫다.

## 4. 복원

`facebook/map-anything-apache` 를 쓴다. 저장소와 가중치 모두 Apache-2.0 이고
승인 절차가 없다. 기본판 `facebook/map-anything` 은 가중치가 cc-by-nc 이니 가려 쓴다.

가중치가 4.91GB 라 처음 한 번은 내려받는 데 삼 분쯤 걸린다.
**전체 시간의 대부분이 여기다.** 미리 걸어 두고 그동안 다른 걸음을 준비한다.

**계산 능력 7.5 인 GPU(T4 등)에서는 반드시 `amp_dtype="fp16"`.**
공식 예제는 `bf16` 인데 그런 GPU 에는 bf16 이 없어서 계산이 통째로 32비트로 풀리고
메모리가 넘친다. **8장까지는 bf16 으로도 돌기 때문에 작게 시험하면 통과하고
본 실행에서 터진다.** 이걸 모르면 원인을 못 찾는다.

```python
pred = model.infer(views, memory_efficient_inference=True, minibatch_size=1,
                   use_amp=True, amp_dtype="fp16",
                   apply_mask=True, mask_edges=True, apply_confidence_mask=False)
```

16GB GPU 에서 잰 값이다.

| 장수 | 복원 | 최대 메모리 |
|---|---|---|
| 24 | 약 10초 | 6.8GB |
| 32 | 13초 | 7.3GB |
| 64 | 32초 | 9.5GB |
| 96 | 55초 | 12.0GB |
| 128 | 넘침 | |

**사진은 모델이 정한 크기로 줄어서 들어간다.** 비율에 맞는 칸을 고정된 표에서 고르고
16:9 면 518×294 다. 원본이 4K 여도 마찬가지이고 올릴 수 없다.
케이블이나 의자 다리처럼 가는 것이 뭉개지는 까닭이 여기 있다.
사용자가 그 부분을 더 또렷하게 원하면 **장수를 늘리는 것보다 그 앞에서 더 찍는 편**이 낫다.

## 5. 점 다듬기

**멀리 튄 점을 버린다.** 창밖과 거울에 비친 것이 엉뚱하게 먼 거리로 잡히는데,
두면 장면이 한없이 커지고 다음 걸음의 알갱이 크기 기준이 망가진다.
각 축 0.5 ~ 99.5 백분위 밖을 버리면 된다.

**카메라가 실제로 움직였는지 본다.**

```
카메라가 움직인 폭 / 장면 대각선
```

**0.1 보다 작으면** 제자리에서 돌기만 한 것이라 결과가 대개 무너진다.
여기서 **[물어본다]**. 그대로 가 볼지, 다시 찍을지 정한다.
그대로 가면 아치 모양으로 휘어 나올 가능성이 높다는 점을 함께 밝힌다.

## 6. 알갱이로 바꾸기

점은 크기가 없어 화면을 못 채운다. 점 하나를 부피와 투명도를 가진 알갱이로 바꾼다.

가우시안 스플랫 `.ply` 의 칸은 원래 **62개**다.

| 칸 | 개수 | 어디서 오나 |
|---|---|---|
| 자리 | 3 | 점 |
| 법선 | 3 | 안 쓴다. 0 |
| 기본 색 | 3 | 점 색. 구면 조화 0차라 `(색/255 - 0.5) / 0.28209479177387814` |
| 각도별 색 | 45 | **없다.** 학습을 걸어야 채워진다 |
| 불투명도 | 1 | 정한다. 로짓으로 저장하므로 0.9 면 `log(0.9/0.1)` |
| 크기 | 3 | 정한다. **로그로 저장한다** |
| 회전 | 4 | 근거가 없으니 안 돌린 사원수 `(1,0,0,0)` |

**각도별 색 45칸은 헤더에 아예 넣지 않는다.** 0 으로 채워 적으면 파일만 3.6배가 된다.
빼면 칸이 17개, **알갱이 하나에 68바이트**다.

**알갱이 반지름.** 알갱이가 덮는 넓이가 반지름의 제곱에 비례하니, 점 N 개로 표면을
덮으려면 반지름이 N 의 제곱근에 반비례해야 한다.

```
r = K * (장면의 가장 긴 변) / sqrt(N)      K = 1.4 로 시작
```

**이웃 점까지의 거리를 기준으로 삼지 않는다.** 점이 사진마다의 깊이에서 나오다 보니
가장 가까운 이웃은 늘 같은 사진 안의 옆 화소라, 점을 열 배 줄여도 이웃 거리가
두 배도 안 늘어난다. 기준이 못 된다.

**좌표를 뒤집는다.** 이 모델은 Y 가 아래를 향하고 three.js 는 Y 가 위다.
y 와 z 의 부호를 뒤집지 않으면 장면이 거꾸로 선다.

결과를 띄워 보고 **[물어본다]**. 구멍이 보이면 K 를 올리고 뭉개지면 내린다.
어느 쪽인지는 보는 사람이 정할 일이다. 고친 값으로 다시 만드는 데는 몇 초면 된다.

## 7. 줄이기

**건너뛸 수 없는 걸음이다.** 알갱이 320만 개면 `.ply` 가 217MB 인데
깃허브는 파일 하나에 100MiB 가 한계다.

```bash
npx -y @playcanvas/splat-transform@latest -w input.ply output.sog
```

`-w` 를 빼면 파일이 이미 있을 때 덮어쓰지 않고 멈춘다.

| 형식 | 알갱이 100만 개 기준 | 배수 |
|---|---|---|
| `.ply` | 68.0MB | 1 |
| `.splat` | 32.0MB | 2.1 |
| `.compressed.ply` | 16.3MB | 4.2 |
| `.sog` | 5.0MB | 13.6 |

배수는 장면과 개수에 따라 달라진다. 320만 개짜리는 217.5MB 가 15.3MB 로 14.2배였다.

크기를 말할 때 **어느 기준인지 밝힌다.** 1,000,000 으로 나누면 15.3, 1048576 으로
나누면 14.6 이다. 같은 파일인데 도구마다 다르게 찍혀서 헷갈리기 쉽다.

## 8. 띄우기

three.js 와 Spark 를 쓴다. **함정이 셋 있고 셋 다 조용히 실패한다.**

**하나.** `SparkRenderer` 를 장면에 넣지 않으면 알갱이가 다 올라가고도 화면이 까맣다.
오류도 안 난다.

```js
scene.add(new SPARK.SparkRenderer({ renderer }));
```

**둘.** 확장자와 Spark 안쪽 이름이 다르다. `.sog` 는 `pcsogszip` 이다.

```js
new SPARK.SplatMesh({ fileBytes: bytes, fileType: 'pcsogszip' });
```

**셋.** `Box3.setFromObject` 가 `SplatMesh` 에는 빈 상자를 준다. 일반 메시가 아니라
three 가 크기를 못 잰다. 카메라를 맞추려면 범위를 파일에서 따로 재 둔다.

새로 짜기 전에 https://github.com/SunCreation/room-3d-demo 의 `index.html` 을 본다.
셋을 다 처리한 판이다.

## 9. 올리기

**[물어본다]** 먼저 확인받는다. **공개 저장소에 올리면 찍은 공간이 그대로 공개된다.**
집이나 사무실이면 그대로 보인다. 되돌리려면 저장소를 지워야 하고, 그 사이 누가

python3 -m http.server 8777

`.nojekyll` 은 깃허브가 파일 이름을 임의로 손대지 않게 하는 표시다.

## 10. 물리를 붙이려면 메시가 따로 필요하다

**[물어본다]** 여기까지 갈지 확인한다. 화면에 띄우기만 할 것이면 필요 없는 걸음이다.

**알갱이는 부딪히지 않는다.** 그리기 위한 것이라 딛고 설 면이 없다.
물체를 올려 놓고 움직이게 하려면 삼각형 메시를 따로 뽑아야 한다.

포아송 표면 복원(`create_from_point_cloud_poisson`)이 정석이지만
등위면을 뽑는 단계에서 **파이썬 예외가 아니라 프로세스째 죽는 일**이 있다.
`try` 로 못 잡으니 다음 설정으로 넘어가지도 못한다.
그러면 격자로 가는 편이 확실하고 훨씬 빠르다.

```
점을 격자에 찍는다  →  형태 연산으로 구멍을 메운다 (binary_closing)
 →  흐린다 (gaussian_filter)  →  등위면을 뽑는다 (marching_cubes)
 →  떠 있는 부스러기 덩어리를 버린다  →  타우빈으로 다듬는다  →  삼각형 수를 줄인다
```

메우는 정도를 반지름으로 정할 수 있다는 것이 이 길의 이점이다.
타우빈은 라플라시안과 달리 부피가 덜 쪼그라든다.

**안 찍힌 곳은 색을 가져올 데가 없어 검게 남는다.** 꼭짓점마다 가까운 점까지의 거리를
재서 본 곳과 지어낸 곳을 가르고, 지어낸 곳은 이웃 평균을 여러 번 되풀이해 채운다.
이웃 평균 반복이 라플라스 방정식을 푸는 것과 같아서 가장자리 색이 매끄럽게 이어진다.

물체를 어디에 올릴지는 **수평면이 몰린 높이**를 세면 찾을 수 있다.
법선의 세로 성분이 1 에 가까운 꼭짓점을 높이별로 세면 바닥과 천장이 가장 크게 잡히고,
그 사이에 책상이나 선반이 나온다.

## 무엇을 보고 판단하나

| 걸음 | 확인 | 정상 |
|---|---|---|
| 사진 뽑기 | 장수와 번짐 | 24장, 번진 장이 한둘 |
| 복원 | 점 개수 | 24장이면 300만 개 안팎 |
| 복원 | 카메라 퍼짐 / 장면 대각선 | 0.1 보다 큼 |
| 알갱이 | 파일 크기 / 알갱이 개수 | **68**. 다르면 헤더가 잘못됐다 |
| 알갱이 | 헤더에 `f_rest` 가 있는가 | 없어야 한다 |
| 줄이기 | `.sog` 크기 | 100MiB 아래 |
| 띄우기 | 화면에 찍힌 알갱이 개수 | 0 이면 파일을 못 읽은 것 |
| 띄우기 | 각도를 크게 틀 때 | 앞뒤가 뒤집히지 않음 |

## 안 될 때

| 증상 | 원인 |
|---|---|
| 복원에서 메모리가 넘침 | `bf16` 을 쓰고 있다. `fp16` 으로 바꾼다 |
| `import mapanything` 실패 | `sys.path` 를 안 끼웠다 |
| 장면이 거꾸로 섬 | y, z 부호를 안 뒤집었다 |
| 장면이 한없이 큼 | 멀리 튄 점을 안 버렸다 |
| 표면에 구멍이 숭숭 | 반지름 K 가 작다. 또는 점이 너무 적다 |
| 다 뭉개짐 | K 가 크다 |
| 아치 모양으로 휘어 나옴 | 제자리에서 돌며 찍었다. 다시 찍어야 한다 |
| 화면이 까만데 오류가 없음 | `SparkRenderer` 를 안 넣었다 |
| `Invalid file type` | `.sog` 인데 `sog` 라고 적었다. `pcsogszip` 이다 |
| 깃허브가 파일을 거부 | 100MiB 를 넘었다. `.sog` 로 줄인다 |
| 각도를 틀면 검은 자리 | 안 찍힌 면이다. 그쪽을 더 찍어야 한다 |
| 코랩 명령이 응답이 없음 | 전달이 안 된 것이다. `colab status` 로 보고 다시 건다 |
